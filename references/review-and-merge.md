# 审查与合并（Review and Merge）

## 1. 审查顺序

1. 每个 PR 必须先过一审。
2. 属于二审范围（§3）的 PR，再过二审。
3. 一审与二审结论互不替代；两者应来自不同账号。
4. 一个 PR 合并前至少有两道审查，其中至少一道来自与实现者不同的成员或模型；主管审 diff 与 CI 可计为一道。

## 2. 一审

1. 一审 Agent 逐行全量审查全部非生成文件；生成物与二进制可扫读或核校验值，并在结论中标注。
2. 开审时比对 PR head 与 main 的 sha；复审只审增量，并逐条核对修正单。
3. 结论发在被审 PR 评论，格式见 `templates/review.md`，结论栏包括：覆盖、CI run 与 jobs、自报缺口、是否需二审、新鲜度、体量、规格符合、问题分级、落脚点、界面用语、结论。
4. 结论取值：
   - 「可合并」：无未清问题；
   - 「带条件通过」：仅余 Minor，逐条列出条件；作者修改后由主管核 diff 符合即可合并，不回一审复审；
   - 「不可合并」：存在 Critical 或 Important，修复后必须复审。
5. 审查必须当轮完成，不得攒批。

## 3. 二审

1. 二审范围：
   1. 鉴权；
   2. 契约；
   3. 数据迁移；
   4. 隐私与账号删除；
   5. 部署与 CI；
   6. 密钥；
   7. 上架与发布合规；
   8. 发布前的合并批次。
2. 其余 PR（纯文档、界面小改等）一审通过即可合并。
3. 二审 Agent 对二审范围内的 PR 全量审查；对其他 PR 可抽审，并抽查一审清单。
4. 二审结论必须附当次证据；未核实的写「未验证」。
5. 二审 Agent 不可达时，负责人可一次性书面豁免，并登记决策编号。

## 4. 合并门

合并前由主管写合并门记录（`templates/merge-gate-record.md`），不得写在被审分支上。以下八项必须全部通过：

1. **覆盖**：变更文件数与逐行读数；生成物与二进制的处理方式已标注。
2. **执行检查**：每类文件（代码、配置、文档、图片等）对应一个实际运行过的检查。跳过的检查必须写明理由、替代验证与兑现点，未兑现前挂账。没有被编译过的代码文件不算通过。
3. **自报缺口**：作者列出的缺口逐条关闭，或由负责人书面豁免（登记豁免人、内容、依据）。
4. **二审**：属于二审范围的，已有二审结论且无未清阻断项。
5. **新鲜度**：PR 上 CI 汇总检查通过，记录 head sha；sha 变化则重核第 2、4 项，旧授权作废。属于 §7.3 情形的，已先同步 main 并重跑 CI。
6. **体量**：约 40 个文件或 1000 行以上的，已拆分，或已说明不能拆分的理由与覆盖分工。
7. **落脚点**：已写明产出在哪里被读取、用户看到什么结果（文件与行，或界面位置）；写不出的退回。
8. **界面用语**：界面文字均为成熟商业表达；品牌化口语句已明确标注；未标而口语化的退回，拿不准的列「待负责人」。

分歧写入合并门记录，不得私下消化。

## 5. 问题分级

| 级别 | 处理 |
|---|---|
| Critical | 立即修复，修复后复审 |
| Important | 合并前修复，修复后复审 |
| Minor | 可带条件通过；由主管记录并直接派单 |

## 6. 规则预授权合并

1. 同时满足以下条件时，主管可直接 squash 合并（指定 head sha），事后在汇报中列出 PR 号与 head sha：
   1. 一审结论为「可合并」，或「带条件通过」且条件已由主管核 diff 确认；
   2. 属于二审范围的，二审已通过；
   3. CI 全绿；
   4. 合并门八项全部通过。
2. 部署、密钥、CI 配置类 PR 必须由负责人逐单授权。
3. 需要负责人决定的事项必须先问；主管自定的口径必须在汇报中说明，负责人可推翻。
4. 草稿 PR 必须先标记 ready 才能合并（直接合并草稿会被平台拒绝）。
5. 每次合并在状态流水登记 PR 号与 head sha。

## 7. 合并流程

1. **审完当轮就合。** 审查给出可合并结论后，主管或巡检当轮写合并门记录并合并。
2. **不排死队列。** 卡住的 PR 跳过，记录卡点与等待对象。
3. **每个 PR 都有负责人和下一步。** 卡点表每轮刷新；卡在谁那里，当轮为谁准备任务书。
4. **分支保护。** main 只接受 PR 合入；必需检查只保留 CI 汇总检查；线性历史；管理员不得绕过。不要求合并前同步 main，以下情形除外：
   1. PR 改动了自其 base 以来新合入的 PR 碰过的同一批文件；
   2. PR 改动了数据迁移或契约目录。
   上述情形必须先同步 main、等 CI 通过后再合。
5. **按可单独合入切分。** 契约先行；不要求多个 PR 同批合并。

## 8. 合入后验证与回退

1. 每次推送到 main 都运行 CI，按本次推送的改动路径决定 job，口径与 PR 相同，不得被后续推送取消。
2. main 的 CI 变红时，必须立即停止一切合并。
3. 出问题 PR 的作者开回退 PR，内容必须正好是原 squash 提交的反向 diff。满足此条件的回退 PR 免审查、不受在制品上限限制，CI 通过后主管直接合并。
4. main 恢复绿色后才恢复合并；原 PR 修复后重新走审查。
5. 大改或迁移合入后，必须核验大文件对象本体（如 `git lfs fsck`），不得只核指针。

## 9. 叠栈

1. 叠栈最多两层；整串一起审，不等下层合入再审上层。
2. 叠栈 PR 同样触发 CI，合并门第 2 项按实际运行的 CI 核对。
3. 下层合入后，先把上层 PR 的 base 改为 main，再删除下层分支。
4. 上层更新分支失败时，用 `git rebase --onto` 迁移后以 `--force-with-lease` 推送。
5. 两层均已审过时，可先把上层合入下层，整串一次 squash。

## 10. 在制品上限

1. 开着、未合并的 PR（含草稿，不计依赖机器人）默认上限为 5。
2. 派会开 PR 的任务前，主管必须先计数并写入汇报；已达上限时先审、先合，不新开。
3. 调研、审查、不开 PR 的任务不占名额。
4. 例外：线上故障修复、安全修复、回退 PR。
5. 新开工数不应超过合并数；修正单、回报答复与已有 PR 的返工不计为新开工。

## 11. 提速七条

参照 Google Engineering Practices 与 DORA 研究的做法：

1. **带条件通过**：一审仅余 Minor 时给「带条件通过」，作者改完由主管核 diff 即合；Critical、Important 仍须复审。
2. **当轮审**：回报一到即审，不攒批。
3. **二审只给高风险**：范围见 §3。
4. **规格与实现同 PR**：新功能单的规格、实现与测试放同一 PR；二审范围内的鉴权、契约、数据迁移、隐私与账号删除先单独出规格并过二审。
5. **小改动、当天合**：拆到可独立审查、可独立回退的单元；过合并门当天合并。
6. **批量转发**：同一轮的任务书与修正单一次交负责人转发。
7. **机器能核的不靠人**：验收写成可运行命令，门禁与引用检查逐步纳入 CI，人工审查只处理判断题。
