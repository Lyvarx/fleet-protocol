# 执行 Agent 规程（Implementer Guide）

本文是执行 Agent 的通用工作规程，可作为各项目 `AGENTS.md` 的底本。项目应在其上补充：读文件顺序、钉定的工具版本、构建与测试命令、目录边界与安全约束。尖括号内为项目自定项。

## 1. 开工规程

每次开工，以及上下文被压缩后，按顺序执行：

1. 加载项目开工 skill（任务书首行指定）。
2. 列出自己开着的 PR，读上次回报之后的新评论（含修正单、裁定、二审结论）。
3. 读决策公告板自上次以来的新增条目；从任务书留档回读本任务书的最新版本。
4. 先按评论与修正单执行，再做手头的任务书。
5. 冲突时以较新的主管指令为准；无法判断时停手上报。
6. 报告本机环境版本并与项目钉定版本比对；不一致（含未安装）写入 PR 描述「环境」一节，说明哪些检查只能交给 CI。
7. 列「待负责人」事项时，每条必须引用决策编号，或注明「已查公告板，无决策编号」。

## 2. 分支与 PR

1. 开工前必须确认当前不在 main 上。
2. 一个任务对应一条分支、一个 PR；分支从任务书指定的基线拉出（默认最新 main），命名 `task/<任务号>-<短名>`。
3. PR 以草稿开启；标记 ready 与合并由主管处理。
4. 不得直接推送 main；不得 force push 共享分支（叠栈迁移按 `references/review-and-merge.md` §9 使用 `--force-with-lease`）。
5. 依赖未合并分支时，在 PR 正文说明会带上哪些提交。
6. 提交信息使用 Conventional Commits：`feat|fix|docs|test|chore(scope): 描述`。
7. 开 PR 前统计在制品数量；已达上限时停手报主管（故障修复、安全修复、回退 PR 例外）。
8. 单个 PR 以几百行为宜；超过约 40 个文件或 1000 行必须拆分或在 PR 中说明理由。
9. 构建产物与密钥不得入库；密钥一律经环境变量注入。

## 3. 规格与范围

1. 先读规格再写代码；没有方法级规格的，先补规格。
2. 新功能的规格、实现与测试放同一个 PR。鉴权、契约、数据迁移、隐私与账号删除类，必须先单独出规格 PR 并通过二审，再实现。
3. 契约是唯一事实源；改字段、类型、枚举前必须先有决策编号。
4. 只修改任务书允许的目录；需要改范围外文件时停手。
5. 修改已定稿或已实现的功能前，先读源码与原始规格并原样复用；可完善，不得随意删减。
6. 删除字段或接口、判定「无人使用」前，必须用多种命名形式（如 camelCase 与 snake_case）全目录检索，并写明它原本为何存在。
7. 界面文字使用成熟商业产品的表达；有意保留的品牌化口语句必须在规格或任务书中明确标注。
8. 实现只依据本项目规格、公开资料与自有设计；不得引入同类产品的名称、数据或截图。

## 4. 测试先行

1. 先提交失败的测试，再提交实现，然后运行至全部通过。
2. 每个 PR 必须带测试，至少覆盖本次改动的行为。
3. 验收写成可运行命令；作者自行运行并在回报中贴出输出。

## 5. 证据

1. 没有当次运行输出，不得写「通过」；未亲自核实的写「未验证」。
2. CI 结论以 check runs 原始结果为准，回报中写 run 与 job 的标识。
3. CI 全绿是必要条件而非充分条件；任务书要求联调、真机或接口验收时，必须写明命令、环境与结果。
4. 大改或迁移后，必须核验大文件对象本体（如 `git lfs fsck`），不得只核指针文件。
5. 回报发出前必须回读，检查尾部是否截断、是否残留 `truncated` 等字样，逐节清点。

## 6. 停手条件

出现以下任一情况，必须停在最近一个完整提交并上报：

1. 同一原因失败两次；
2. 需要修改任务书允许范围以外的文件；
3. 任务书与已定决策或规格冲突，且无法判断以哪个为准；
4. 需要负责人决定的取舍；
5. 缺少凭据、权限或环境变量（不得猜测，不得要求在聊天中粘贴密钥）；
6. 判定为环境故障（§8）；
7. 额度不足以完成下一个完整步骤；
8. 在制品已达上限且本任务不属于例外。

## 7. 回报

1. 回报写在任务书登记的唯一位置，标题「<任务号> 回报 · head <sha>」，格式见 `templates/report.md`。
2. 有 PR 的：更新 PR 描述（head sha、证据、缺口），并发一条 PR 评论；过程中的提问或补充同样以评论发出。
3. 无 PR 的（推送前、纯调研、额度用尽）：发在任务书留档的评论；不可用时经负责人转发。
4. 回报必须列出自报缺口；每条缺口写明原因与建议处理。

## 8. 环境与自建 runner 故障判定

1. 先区分代码失败与环境故障。以下现象通常属于环境故障：checkout 或依赖下载连接超时、代理不可达、`HTTP2 framing` 类错误、runner 离线或长时间排队。
2. 自建 runner 经代理访问外网时，网络或代理超时属于环境问题：不得为此修改代码或 CI 配置，不得反复重跑。停手，在 PR 描述写明「CI 网络超时，疑似 runner 网络或代理」并附报错原文，由主管与负责人处理。
3. 修改 CI 配置时，自建 runner 的 job 应通过变量选择执行器（如 `${{ vars.<RUNNER_VAR> || 'ubuntu-latest' }}`），不得写死；不得依赖托管 runner 预装而自建机缺失的工具，所需工具用 setup 类 action 或步骤安装；不得在 workflow 中设置或覆盖代理变量。
4. 单台自建 runner 排队较慢属于正常现象。
5. 审查 Agent 读 CI 时同样先作此区分；环境故障不计为 PR 的问题。

## 9. 服务器与生产环境

1. 服务器操作默认 dry-run；只有负责人明确授权后才实际执行。
2. 一次一条命令；写操作前说明目标、影响与回滚方式。
3. 不得执行破坏性命令（删除数据库对象、递归删除、修改安全组等），除非任务书逐项写明并经负责人授权。
4. 代码以仓库为准；服务器只做拉取、构建、迁移、重启。

## 10. 完成定义

任务完成必须同时满足：

- [ ] 实现与规格一致；
- [ ] 新增或修改的行为有测试且通过；
- [ ] 项目要求的各端检查命令通过；
- [ ] PR 上 CI 的汇总检查通过；
- [ ] 文档已更新（规格、任务清单、决策记录之一）；
- [ ] 落脚点已写明；
- [ ] 界面文字合规，品牌化口语句已标注；
- [ ] 回报已按格式发在登记位置。
