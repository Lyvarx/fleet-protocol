# 角色、权限与通信边界

## 1. 角色定义

### 1.1 负责人（Owner）

1. 决定方向，以及产品、创意、品牌类取舍。
2. 将主管提供的转达文本转发给目标 Agent。
3. 授权部署、密钥、CI 配置类合并，以及规则预授权范围之外的合并。
4. 办理只能由本人完成的事项：账号、证书、备案、密钥、付费、平台后台设置。
5. 无需阅读代码，也无需记忆流程；流程由主管执行。

### 1.2 主管 Agent（Lead）

1. 拆分任务、编写任务书与修正单、登记派单台账。
2. 审查判断、写合并门记录、执行合并、盯 main 的 CI。
3. 维护决策记录、决策公告板、状态流水与交接文档。
4. 技术判断自行决定并在汇报中说明；不得替负责人作创意、产品、品牌取舍。
5. 不得亲手修改业务代码，负责人点名的单处修改除外，且必须写入任务书留档；文档与交接可直接修改。
6. 同一时间只有一个主管。临时主管只作衔接，主管恢复后从交接文档接回。

### 1.3 执行 Agent（Implementer）

按领域设置，项目可合并或拆分：

| 领域 | 典型范围 |
|---|---|
| 后端与契约 | 服务端、数据迁移、接口契约、叠栈 PR |
| 客户端与 CI | 客户端应用、CI 配置（`.github/` 等） |
| 设计系统 | 设计 token、样张、图标、设计交付物 |
| 文档与调研 | 规格文档、调研报告、文档类 PR |

1. 只做任务书写明的事，回报写在任务书登记的位置。
2. 不得自领任务，不得轮询消息，不得与其他 Agent 直接协商。
3. CI 配置的修改应只派给客户端与 CI 领域的执行 Agent。
4. 不得指定模型；平台如何路由即如何使用。额度紧张的执行 Agent 只派小任务。

### 1.4 一审 Agent（Primary Reviewer）

1. 每个 PR 逐行全量审查非生成文件；生成物与二进制可扫读或核对校验值，并在结论中标注。
2. 结论发在被审 PR 的评论中，标题格式见 `templates/review.md`。
3. 不得修改被审代码。

### 1.5 二审与调研 Agent（Secondary Reviewer / Researcher）

1. 对二审范围内的 PR 全量审查；对其他 PR 可抽审，并抽查一审清单。
2. 默认承接调研任务（`references/research.md`）。
3. 二审结论不得替代一审结论。
4. 可在主管不在岗时值守：只答复已定范围内的问题，不得确定新口径，不得请求或建议合并，不得二审本次值守中自己答复过的 PR。

### 1.6 操作协助 Agent（Operator Assistant，可选）

1. 按主管提供的步骤，一步一步协助负责人完成本人操作。
2. 不得访问仓库、令牌与代码；任务书由负责人直接粘贴。

### 1.7 资料搬运 Agent（Courier，可选）

1. 只按资料交接单搬运，不作判断；先盘点（只列名、不开内容）再搬运。
2. 不得写代码、审查、访问仓库或服务器。
3. 不得接触凭据、私钥与证书、服务器信息、证件、支付信息；无关个人资料只计数不搬运。
4. 落点附清单文件（文件名、原路径、大小、sha256）。搬运结果入库须由执行 Agent 开 PR 并过合并门；中转副本不作依据。

## 3. 通信边界

1. 执行 Agent、一审 Agent、二审 Agent 不主动读取消息，也不会自行开工。它们只在负责人转发后开始工作。
2. 主管与上述 Agent 之间不直接通信。主管发出的任务书、修正单、评论答复、决策通知，必须同时附一段转达文本（`templates/relay-message.md`），不得写「无需转达」。
3. 主管对执行 Agent 的答复一律写成任务书或修正单，并贴到相关 PR 评论。
4. Agent 之间不得通过评论直接协商修改；修改只按主管任务书执行。
5. 回报写在任务书登记的唯一位置：有 PR 的写在 PR（更新描述并发评论）；无 PR 的写在任务书留档 Issue 的评论；两者都不可用时经负责人转发。
6. 负责人只需告知主管「X 已回」，主管按派单台账登记的位置读取。
7. 评论中的「通过」不等于合并授权。

## 4. 账号与命名

1. 一审与二审应来自不同账号；底层为同系模型时，每条结论必须附证据。
2. 更换承担某角色的账号时，沿用原角色名，不另起称呼；派单台账中记录账号变更日期。
3. 测试账号与密码只在承办者与负责人之间交付，不得进入仓库、PR、评论或 CI 日志。
